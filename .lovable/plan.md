# Phase 2 — Club Members Foundation (v4)

Документ дополняет утверждённые `v1` (архитектура), `v2` (User Flows) и `v3` (business rules / future compatibility). Архитектура, пользовательские сценарии и порядок реализации Phase 2.1 … 2.8 **не меняются**. Раздел ниже — только продуктовая философия и документационный roadmap.

---

## I. Platform Philosophy

Долгосрочные продуктовые принципы платформы. Действуют во всех будущих фазах и имеют приоритет над любыми будущими фичами, которые им противоречат.

### 1. Разделение идентичностей

Платформа строго разделяет **Platform Identity** и **Club Identity**. Это две независимые сущности, которые никогда не смешиваются и не «протекают» друг в друга.

**Platform Identity (владелец — сам пользователь, хранится централизованно):**
- аккаунт (`auth.users`);
- никнейм (`profiles.display_name`);
- e-mail;
- аватар;
- пользовательские настройки (язык, тема, уведомления и т. п.).

Platform Identity одинакова во всех клубах пользователя и не зависит от клубной активности.

**Club Identity (владелец — конкретный клуб, хранится в рамках клуба):**
- клубный ник (`club_members.display_name`);
- роль в клубе (`club_members.role` + mirror в `user_roles`);
- Player Dossier (реальное имя, телефон, приватные заметки клуба);
- внутренние заметки о поведении;
- VIP-статус;
- штрафы (penalties);
- достижения (achievements);
- долги (debts);
- статистика (games, buy-ins, cash-outs, sessions);
- любые другие клуб-специфичные данные.

Club Identity существует **только внутри одного клуба** и никогда не автоматически переносится в другой клуб, даже если это тот же `user_id`.

### 2. Роль платформы

Платформа предоставляет **только инфраструктуру**: аутентификацию, хранение, RLS, RPC, UI-оболочку, аудит. Она не выступает арбитром между клубами и не владеет операционными данными.

**Каждый клуб полностью владеет своими операционными данными и досье игроков.** Данные клуба — собственность клуба; платформа лишь гарантирует их изоляцию и сохранность.

### 3. Явные запреты (permanent)

Следующие возможности архитектурно запрещены и не будут добавлены ни в одной будущей фазе:

- **Глобальные рейтинги игроков.** Никаких кросс-клубных таблиц лидеров, глобальных VIP-уровней, платформенной репутации.
- **Единая база игроков.** Нет общей коллекции «всех игроков платформы», доступной клубам.
- **Кросс-клубные досье.** Player Dossier одного клуба недоступно другому клубу, даже если это тот же `user_id`.
- **Автоматический обмен информацией между клубами.** Никакая клубная информация (заметки, штрафы, долги, статистика, VIP) не «синхронизируется» в другие клубы без явного экспорта клубом-источником и явного импорта клубом-получателем (и то — только как будущая опциональная фича, не по умолчанию).
- **Платформенные сигналы «плохой игрок».** Платформа не помечает пользователей на основе действий в других клубах.

Эти запреты — часть контракта с клубами и с игроками; их нарушение недопустимо.

### 4. Operational History Lifecycle (обобщение раздела F из v3)

Sesons / Archive из v3 обобщается в общий жизненный цикл операционных данных клуба. Действует для всех будущих операционных модулей (Games, Cash, Expenses, Reports, Sessions и т. д.).

Owner клуба управляет операционной историей клуба через три независимых действия:

- **Export.** Owner-controlled выгрузка операционных данных за период / сезон / модуль (CSV / JSON). Всегда доступна, всегда явная.
- **Archive.** Перевод операционных данных в архивный срез (read-only, вне повседневных отчётов). Обратимая операция.
- **Delete (optional).** Необратимое удаление операционных записей за период. Разрешено только после явного экспорта; UI обязан требовать подтверждения.

Инварианты жизненного цикла (расширение v3 §F):

- `club_members` **никогда не участвуют** в archive/export/delete. Идентичность участников сохраняется всегда, независимо от того, что произошло с операционной историей.
- `audit_log` **никогда не удаляется** операционным жизненным циклом. Аудит — отдельный неизменяемый слой.
- Archive / Delete применяются **только к операционным модулям** (Games, Cash, Expenses, Sessions, Buy-ins, Cash-outs, Debts, Reports, Statistics-производные).
- Delete без предварительного Export не предлагается по умолчанию.
- Все три операции — owner-controlled и логируются в `audit_log`.

Смысл принципа: клуб может «начать сезон с чистого листа», не теряя ни своих участников, ни аудита действий Owner-а.

## J. Future Product Roadmap (appendix, documentation-only)

Список планируемых бизнес-модулей. **Не меняет порядок реализации Phase 2 и не является планом работ.** Приведён для того, чтобы будущие проектные решения принимались с учётом полного контекста.

Каждый модуль обязан следовать инвариантам v3 §D и §G — единственная ссылка на человека внутри модуля: `club_member_id`.

| Модуль                        | Назначение (кратко)                                                                 |
| ----------------------------- | ----------------------------------------------------------------------------------- |
| **Player Dossier**            | Клубное досье игрока: реальное имя, контакты, заметки. Владелец — клуб.             |
| **Games**                     | Игровой движок клуба: игры, столы, места, раздачи.                                  |
| **Cash**                      | Кэш-леджер клуба: buy-ins, cash-outs, банк сессии.                                  |
| **Expenses**                  | Затраты клуба: аренда, зарплаты дилеров, инвентарь.                                 |
| **Accounting**                | Внутренняя бухгалтерия клуба: сводки прибыли/убытка, взаиморасчёты.                 |
| **Reports**                   | Отчёты по периоду / сезону / участнику / столу.                                     |
| **Statistics**                | Агрегаты по игрокам и клубу (в рамках одного клуба).                                |
| **Achievements**              | Клубные достижения игроков. Никаких кросс-клубных достижений.                       |
| **VIP**                       | Клубная VIP-программа. Уровень принадлежит клубу, не платформе.                     |
| **CRM**                       | Работа Manager/Owner с базой игроков клуба: сегменты, касания, повторные визиты.    |
| **Notifications**             | Внутриплатформенные уведомления (заявки, роль, приглашения, события клуба).         |
| **Platform Administration**   | Инструменты Creator: управление клубами, Support Mode, системные операции.          |
| **Mobile Companion**          | Мобильный клиент для игроков и дилеров.                                             |
| **Online Club Support**       | Поддержка онлайн-форматов клуба (онлайн-столы, удалённые сессии).                   |

Правила для всех модулей списка:

- Идентификация участника — только `club_member_id` (v3 §D).
- Данные модуля принадлежат клубу; кросс-клубный доступ запрещён (I §3).
- Операционные данные модуля подчиняются Operational History Lifecycle (I §4).
- Никакой модуль не расширяет Platform Identity (I §1).
